# DHCP, APNs и раздача через Happ — 6 октября 2026

## Текущее исправление: 1.4.0

На iPhone установлен local.happvpnpushroute версии 1.4.0. Профиль: IncludeAllNetworks=false, EnforceRoutes=false, ExcludeAPNs=false, ExcludeLocalNetworks=true. Правила IP-маршрутизации не добавляются. Отдельный модуль работает в apsd и привязывает только создаваемые APNs-соединения к активному VPN через параметры Network.framework.

Привязка обычных сокетов не перехватывала push-канал: служба использует channel-flow Network.framework. Сборка arm64 также не загружалась в системный arm64e-процесс. Подписанная сборка arm64e PAC00, созданная Procursus clang 16.0.0 и ld64 951.9, загрузилась и перехватила создание соединения.

Пробная версия привязывалась к utun5. В окончательной версии интерфейс выбирается из текущего SCDynamicStore; номера и UUID не зашиты. Изменяется копия параметров выбранного соединения. Для 5223 достаточно процесса apsd; для 443 требуется имя push.apple.com или поддомен. Посторонний HTTPS не выбирается по принадлежности к адресному блоку Apple. При отсутствии подходящего VPN или нужного API исходные параметры сохраняются.

## Проверено

- В окончательном модуле после запуска apsd: лог APNs connection port=5223 VPN interface=23; сетевой журнал показывает required interface: utun5(23), завершение TCP/TLS-подключения и Connected response ok for default user? YES. TCP-соединение с исходным адресом VPN 198.18.0.1 имеет состояние ESTABLISHED.
- После выключения и повторного включения VPN без перезапуска apsd служба снова подключилась через VPN. После установки пакета: 198.18.0.1:64648 → 17.57.146.29:5223, ESTABLISHED, процесс apsd 10806.
- Полный DHCP-цикл синтетического клиента через USB-раздачу: DISCOVER → OFFER → REQUEST → ACK, выдан 172.20.10.6. Затем отправлен DHCP RELEASE. Реальный IP USB-адаптера компьютера оставался 172.20.10.3. Это проверяет DHCP-службу и путь через bridge100/en1; повторное подключение реального Wi-Fi-клиента в версии 1.4.0 ещё требует подтверждения пользователя.
- HTTPS с iPhone через системный API: example.com, github.com, www.cloudflare.com — HTTP 200. Такие же три запроса с компьютера, явно привязанные к USB-раздаче 172.20.10.3, также вернули HTTP 200.
- Проверка установленных хуков в отдельном процессе: попытки выставить IncludeAllNetworks=true, EnforceRoutes=true, ExcludeAPNs=true, ExcludeLocalNetworks=false дали false, false, false, true.
- 17 тестов выбора APNs прошли. Фильтр исключает обычный HTTPS, имена с неверной границей домена и DHCP-порты.
- В пакете подтверждены подписанные arm64 и arm64e PAC00 slices нового модуля и модуля профиля. Прежняя библиотека DNS сохранена точно. 28 тестов DHCP/DNS-парсера соседнего проекта прошли ранее; его код здесь не менялся.

Работа push-канала подтверждена до ответа сервера APNs. Доставка конкретного уведомления, Wi-Fi-подключение второго телефона в итоговом пакете, специально вызванный fallback 443 и сценарий блокировки экрана пока не подтверждены. Пользователю отправлен запрос на проверку Wi-Fi, обычного интернета и уведомления.

## Исходная проблема

Прежний модуль профиля принудительно устанавливал IncludeAllNetworks=true. При активном VPN DHCP DISCOVER приходили на bridge100, но OFFER не было. bootpd был зарегистрирован с UDP 67 в launchd, однако не запускался от этих запросов. Принудительный запуск bootpd также не восстановил ответы. Сбоя процесса или прямого столкновения хуков не обнаружено.

При IncludeAllNetworks=false пользователь ранее подтвердил выдачу IP Wi-Fi-клиенту. Одновременно apsd выбирал pdp_ip0 и получал отказ TCP 5223 на прямом сотовом пути. Это потребовало отдельного решения для push.

По исходникам Apple bootpd устанавливает SO_RECV_ANYIF, SO_TRAFFIC_CLASS=SO_TC_CTL и IP_RECVIF. XNU отдельно проверяет NECP-политику при получении UDP; разрешение приёма с любого интерфейса не отменяет проверку туннельной политики. Это поддерживает направление диагностики, но не доказывает точное место потери DHCP на закрытой части iOS.

## Неудачная версия 1.3.0

В 1.3.0 использовались EnforceRoutes=true и включённый маршрут 17.0.0.0/8. DHCP и APNs работали в узких проверках, однако пользователь сообщил о поломке остального интернета. Версия полностью откатана до 1.2.0: обе прежние библиотеки восстановлены из точных резервных копий, профиль возвращён к исходным флагам. Неудачный пакет находится только в ignored work/build с пометкой FAILED. Не использовать его.

В 1.4.0 эта стратегия отсутствует: EnforceRoutes выключен, IP-блок Apple не используется как маршрут. Параметры выбираются внутри службы push для конкретного соединения.
